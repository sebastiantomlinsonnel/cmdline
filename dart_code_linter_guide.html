Dart Code Linter guide

Every rule, metric and command in dart_code_linter 4.4.3, what each one does, and how to turn it on. Taken from the package source on this machine (Dart 3.13.5).

Quick start

  1. Add the package as a dev dependency (you already did this): 
    dart pub add --dev dart_code_linter
  2. Pick rules in analysis_options.yaml. Start from a preset and add the IDE section: 
    include: package:dart_code_linter/presets/recommended.yaml

plugins:
  dart_code_linter:
    diagnostics:
      avoid-dynamic: warning
      no-magic-number: warning

dart_code_linter:
  rules:
    - no-magic-number:
        allowed: [-1, 0, 1, 42]
  3. Restart the analysis server in your IDE so it reloads the config.
  4. Run it: 
    dart analyze                                   # issues the IDE plugin shows
dart run dart_code_linter:metrics analyze lib  # full report with metrics

How the config works

On Dart 3.10 and newer, two sections of analysis_options.yaml do different jobs. Most setup confusion comes from filling in only one of them.

plugins: dart_code_linter: diagnostics:

Turns rules on for the IDE and dart analyze. Each value is a single word: true, false, info, warning or error.

dart_code_linter: rules:

Turns rules on for the command-line tool and holds each rule's options. The IDE plugin reads options from here too.

dart_code_linter: metrics:

Thresholds for code metrics, such as maximum complexity. Only the command-line tool reports these.

dart_code_linter: anti-patterns:

Larger design smells (long methods, long parameter lists). These use the metric thresholds.

Full shape of the file

include: package:dart_code_linter/presets/recommended.yaml   # optional preset

plugins:
  dart_code_linter:
    diagnostics:
      rule-id: true | false | info | warning | error

dart_code_linter:
  rules-exclude:          # files no rule checks
    - lib/generated/**
  rules:
    - simple-rule         # on, default settings
    - rule-with-options:
        severity: style
        exclude: [test/**]
        some-option: value
  metrics:
    cyclomatic-complexity: 20
  metrics-exclude:
    - test/**
  anti-patterns:
    - long-method
    - long-parameter-list
On Dart 3.13, keep the diagnostics values to a single word. Putting a map under a rule there (for example no-magic-number: {allowed: [42]}) causes an invalid_section_format error. Put rule options under dart_code_linter: rules: instead.
To turn a rule off completely, remove it from both sections. To turn off a rule that a preset adds, write - rule-id: false under rules:.

Severity levels

Every rule has a default severity. Change it per rule with severity: under dart_code_linter: rules: (command line), or with the value under diagnostics: (IDE).

LevelMeaningCommand-line exit code
errorAlmost certainly a bug or a broken conventionAlways fails the run
warningLikely problem, worth fixingFails by default (--fatal-warnings is on)
performanceWorks, but slower than it needs to beFails only with --fatal-performance
styleReadability and consistencyFails only with --fatal-style
noneRule runs but reports nothingNever

Metrics

Metrics measure your code instead of flagging single lines. Set a threshold under dart_code_linter: metrics: or pass it as a flag, for example --cyclomatic-complexity=15. Only dart run dart_code_linter:metrics analyze reports metrics.

MetricMeasuresApplies toDefault
 
dart_code_linter:
  metrics:
    cyclomatic-complexity: 20
    maximum-nesting-level: 5
    number-of-parameters: 4
    source-lines-of-code: 50
  metrics-exclude:
    - test/**

Anti-patterns

Design problems detected from metrics. List them under dart_code_linter: anti-patterns:. Both report as warnings.

Anti-patternWhat it flagsUses threshold
long-methodFunctions and methods with too many lines of real codesource-lines-of-code (default 50)
long-parameter-listFunctions that take too many parameters. Group them into a class instead.number-of-parameters (default 4)
dart_code_linter:
  anti-patterns:
    - long-method
    - long-parameter-list

Presets

Ready-made rule lists. Use one with include: package:dart_code_linter/presets/<name>.yaml. Presets fill dart_code_linter: rules: only, so the IDE section still needs its own entries.

PresetContents
recommended.yamlA balanced starter set of about 23 rules, plus the long-method and long-parameter-list anti-patterns. You use this one.
metrics_recommended.yamlRecommended metric thresholds
dart_all.yamlEvery pure-Dart rule
flutter_all.yamlEvery Flutter rule
flame.yamlRules for the Flame game engine
intl.yamlRules for package:intl translations
all.yamlEverything. Very noisy, mostly useful for exploring.
You can include several files: include: [package:lints/recommended.yaml, package:dart_code_linter/presets/recommended.yaml]. That also turns on the Dart team's lints package, which is already in your dev dependencies.

Ignoring issues

ScopeHow
One line// ignore: no-magic-number on the line above
Whole file// ignore_for_file: avoid-dynamic, no-magic-number at the top
IDE quick-fix form// ignore: dart_code_linter/no-magic-number also works
Some files, one ruleexclude: on that rule (see Options every rule has)
Some files, all rulesrules-exclude: / metrics-exclude: under dart_code_linter:
Don't use analyzer: errors: for these rules, and skip the IDE quick fix "Ignore … in analysis_options.yaml". The analyzer reports the IDs as unrecognized_error_code and ignores the entry.

Command line

Every command runs as dart run dart_code_linter:metrics <command> [options] <folders>.

analyze: rules, metrics and anti-patterns

dart run dart_code_linter:metrics analyze lib
dart run dart_code_linter:metrics analyze lib --reporter=html   # writes ./metrics/index.html
dart run dart_code_linter:metrics analyze lib --fatal-style --fatal-performance
FlagWhat it does
-r, --reporterOutput format: console (default), console-verbose, checkstyle, codeclimate, github, gitlab, html, json
-o, --output-directoryFolder for the HTML report (default metrics)
--json-pathFile to write the JSON report to
--<metric-id>=NOverride any metric threshold, e.g. --cyclomatic-complexity=15
-c, --print-configPrint the merged config the tool is using. Useful for debugging presets.
--root-folderProject root (default: current folder)
--excludeGlob of files to skip (default {/**.g.dart,/**.freezed.dart})
--sdk-pathDart SDK path. Only needed when running a compiled executable that can't find the SDK.
--no-congratulatePrint nothing when there are no issues
--[no-]verboseDetailed logs
--set-exit-on-violation-levelExit with code 2 when a metric reaches noted, warning or alarm
--[no-]fatal-warningsFail on warning-level issues (on by default)
--[no-]fatal-performanceFail on performance issues
--[no-]fatal-styleFail on style issues
--fatal-*-threshold=NFail only once there are at least N issues of that type (warnings / performance / style)

check-unused-code: dead code

dart run dart_code_linter:metrics check-unused-code lib
FlagWhat it does
--[no-]monorepoTreat exported code as unused unless something in this repo uses it
--analyze-private-membersAlso report unused private methods, fields, getters and setters inside classes
--analyze-public-membersAlso report unused public members. Less reliable, because code used through reflection or code generation looks unused.
--suggest-private-membersReport public declarations only used in their own file, which could be made private
--[no-]fatal-unused / --[no-]fatal-could-be-privateWhether those findings fail the run (both on by default)

check-unused-files: files nothing imports

dart run dart_code_linter:metrics check-unused-files lib
FlagWhat it does
--[no-]monorepoTreat exported files as unused by default
--[no-]fatal-unusedFail when unused files are found (on by default)
-d, --delete-filesDeletes every unused file. Commit your work first.

check-unnecessary-nullable: ? parameters that are never null

dart run dart_code_linter:metrics check-unnecessary-nullable lib

Flags: --[no-]monorepo and --[no-]fatal-found (on by default).

check-unused-l10n: unused translation strings

dart run dart_code_linter:metrics check-unused-l10n lib -p "I18n$"

Flags: -p, --class-pattern is a regex matching your localization class names (default I18n$), plus --[no-]fatal-unused.

Every command also accepts -r (console or json), -c, --root-folder, --exclude, --sdk-path, --no-congratulate and --verbose.
